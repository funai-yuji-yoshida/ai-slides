    1　まず、たとえ話

    ことばの整理：SQLとデータベース

    注文票の話を、アプリに置きかえてみます。

    データベース（DB）

    情報をしまう、大きな表

    ユーザー、商品、売上などが、入っています。たとえるなら「倉庫」。

    SQL

    倉庫に出す、注文書

    「この条件のものを、ください」という、DB専用の言葉。たとえるなら「注文票」。

    アプリ

    注文書を、自動で書く人

    利用者が入力した言葉を使って、注文書を書き、DBに送ります。

    SELECT * FROM users WHERE username = 'sato'

    日本語にすると：「users表から、usernameがsatoの行を、ください」

    問題は、注文書の中に、利用者の入力が入ること。

    4　対策

    穴にできないもの：並べ替えの項目名

    穴（?）に入れられるのは、「言葉」や「数」だけです。「何で並べ替えるか」の項目名は、穴にできません。この場合は、決めた選択肢の中から選ばせます。

    あぶない例

    // 利用者が sort=price などと指定 db.query(`SELECT * FROM items ORDER BY ${sort}`)

    指定された文字が、そのまま、注文書の一部になります。

    安全な例：選択肢から選ばせる

    const allowed = { price: "price", name: "name" }; const col = allowed[sort] ?? "name"; // 許可した項目だけ db.query(`SELECT * FROM items ORDER BY ${col}`)

    利用者の入力は「選ぶだけ」。注文書に入る言葉は、アプリが決めたものだけです。

    「言葉」は穴あきの注文票。「項目名」は選択肢（許可リスト）。
    5　見分ける

    あぶないコードと、安全なコードを見分ける

    見分けるコツ
    あぶない入力を、「+」「${ }」「f"…{ }」「%」で、文字につなげている
    安全「?」「%s」の穴に、入力を別に渡している

    6　AI生成コード

    AIが作ったアプリは、なぜ確認が必要か

    AIが作ったコードは、動くことが多い一方で、あぶない書き方が混ざる可能性があります。「動く」と「安全」は、別のことです。

    理由 1

    短く書ける方が選ばれやすい

    「入力をつなげる」書き方は、短く書けるため、そのまま出力されることがあります。

    理由 2

    古い書き方も学んでいる

    学習した情報には、あぶない書き方も含まれるため、それを再現することがあります。

    理由 3

    「安全に」と頼んでも、確実ではない

    毎回、正しく直るとは限りません。結果は、人が確認します。

    理由 4

    気づかないまま、公開しがち

    コードを読まずに公開すると、問題があっても、気づけません。

    AIが書いたコードも、人が確認してから、公開する。
